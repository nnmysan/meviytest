# 実データへの移行

ダミーデータと実データは、**取込・集計・分析・表示のコードを共通**にしています。切り替えで変えるのは設定だけです。

| 切り替える設定 | ダミー | 本番 |
|---|---|---|
| プロファイル | `config/profiles/dummy.yaml` | `config/profiles/prod.yaml` |
| 列対応表 | `config/sources/dummy/` | `config/sources/prod/`（現在は列名が `TODO`） |
| 閾値 | `config/thresholds/dummy/`（仮） | `config/thresholds/prod/`（未設定） |
| マスタ・目標・担当 | 生成器が作る架空のもの | 社内で管理しているもの |
| 人の確認結果 | `config/review/dummy/*.csv` | Microsoft Lists から出力 |

## ダミーの値が本番の判断基準にならないための仕組み

- 本番プロファイルは、次がすべて満たされるまで**実行を拒否**します（`tests/test_units.py::test_prod_profile_refuses_provisional_settings`）。
  - 閾値ファイルが `status: approved` で、承認者（`approved_by`）が記入されている
  - すべてのKPI定義が `status: approved`
  - すべてのKPIに本番の閾値がある
  - 列対応表に `TODO` が残っておらず、`status: approved`
- ダミーの閾値は `config/thresholds/dummy/` にだけ置き、本番からは参照しません。
- ダッシュボードは、ダミーのとき全画面の上部に「ダミーデータ（検証用）」と表示し、閾値の状態（provisional）も表示します。

## 最初に決めていただくこと

1. **各KPIの定義**：分母、計上日（受注日・納期・出荷日・発見日のどれで月に振り分けるか）、受注番号単位か明細単位か、見込み原価か実際原価か（[design.md §2](design.md) の表）
2. **組織と明細の紐付け**：受注明細の「課」は担当営業の所属か、生産を担当する課か。組織変更の履歴をどう持つか
3. **為替**：評価に使うレート（予算レート／実績レート）と、そのレートを決める部署
4. **目標の粒度**：全社のみか、法人×商品までか、課までか。月別か
5. **ダッシュボード**：Power BI と DOMO のどちらで提供するか。Power BI のライセンス（Pro／PPU／Fabric）
6. **月次の日程**：確定値が出る日、定例の日、担当者の割り当てルール
7. **閲覧範囲の再確認**：全員が顧客別・担当者別の数値まで見てよいか（欧州法人の顧客データの扱いを含む）

## 実データ接続時に用意していただく情報

| 情報 | 用途 |
|---|---|
| 自社システムが出力できるCSVの一覧と列定義書（見積・受注・出荷/納期・品質不良・各マスタ） | 列対応表の作成 |
| ヘッダーは本物のまま、値を伏せた100行程度のサンプル（顧客名は置換、金額は係数をかける、個人名は削除） | 形式・文字コード・日付書式・キーの一意性の確認 |
| 定時出力の可否、または読み取り専用のDB接続の可否（情報システム部門に確認） | 自動取得の方式決定 |
| 管理ファイル（件数・金額合計）を出力できるか | 欠落・二重出力の検知 |
| 既存の月次報告の過去3〜6か月分 | 集計結果の照合（正解として使う） |
| 過去24か月分のデータ | 閾値のバックテスト、季節性の把握 |
| 組織マスタとその変更履歴、顧客マスタ（業種・規模の区分） | 内訳の軸 |
| 目標値、予算レート | 目標差、円換算 |
| 受注明細の受注日時・数量・材質・サイズ区分・表面処理・熱処理・仕入先コード | 時間別表示、サプライヤ充足率（件数・数量） |
| サプライヤマスタ（コード・名称・法人・サプライヤ担当・上司） | 絞り込み、通知の宛先 |
| 供給能力マスタ（サプライヤ×材質×サイズ×表面処理×熱処理 ごとの日あたり供給可能件数・数量）と更新の方法・頻度 | 充足率の分母 |
| サプライヤへの発注金額（原価と異なる場合はその列） | 発注金額の表示・打ち手の影響額 |
| 法人・サプライヤごとの稼働カレンダー | 供給能力の日数、着地見込みの営業日 |
| Teams の通知先（チャネルまたは個人）と Power Automate の実行環境 | 充足率80%超の通知 |
| KPIごとの担当者・確認者 | アクションの割り当て |

## 切り替え時の確認項目

**列定義**

- [ ] 標準列ごとに、元の列名・意味・型・空欄の意味・例を確認した
- [ ] 取消・返品・赤伝の表し方を確認した（状態列か、マイナス金額か、別伝票か）
- [ ] 税の扱い（税抜/税込）と通貨の持ち方を確認した
- [ ] キー（受注番号＋行番号など）が一意であることを確認した
- [ ] 文字コード・日付書式・桁区切りをサンプルで確認した

**計算式**

- [ ] 各KPIの定義を担当者と合意し、`status: approved` にした（version を記録）
- [ ] 既存の月次報告と過去3〜6か月を照合し、差が ±0.5%（仮）以内、または差の理由を説明できる
- [ ] 目標値と担当者のマスタを登録した

**データ品質**

- [ ] 到着期限と、法人ごとの出力担当を決めた
- [ ] 平常時の行数・欠損率・隔離率を把握した（件数急増減の基準の確認）
- [ ] 過去値の修正がどのくらいの頻度・規模で起きるかを確認した

**サプライヤ**

- [ ] 供給能力マスタの値をサプライヤ担当が確認した（実態と合わない能力は充足率を誤らせる）
- [ ] 発注金額の定義（原価＝発注額でよいか）を確認した
- [ ] 充足率の目標80%と、95%・100%の段階、判定しない最小規模を購買部門と合意した
- [ ] 通知の宛先（担当・上司）と、新規・悪化・解消だけ通知するルールを合意した

**閾値**

- [ ] 過去24か月で遡って判定し、月あたりのアラート件数が運用できる量であることを確認した
- [ ] 過去の既知の問題（納期遅延・品質問題など）を検知できることを確認した
- [ ] 部門長が承認し、`status: approved` と承認者・承認日を記入した

**権限・運用**

- [ ] 着地フォルダ（元データ）にアクセスできる人を限定した
- [ ] 閲覧範囲（全員が顧客別まで見てよいか）を最終確認した
- [ ] 確認結果を入力する Lists と、定例までの手順を決めた
- [ ] 既存の報告と2か月並行運用し、差異がないことを確認した
