# 設計

実装済みの仕組みと、その判断基準をまとめます。「仮」と書いたものはダミーデータ検証のための仮置きで、
実データ接続前に決める必要があります（[migration.md](migration.md)）。

## 0. 前提

| 区分 | 内容 |
|---|---|
| 確定（ヒアリング） | 製造業の受注生産。KPIは受注金額・受注件数・見積→受注転換率・粗利率・納期遵守率・品質不良発生率（追加可能に）。内訳は商品（切削角物・切削丸物・板金・板金溶接）、顧客（顧客名・業種・規模）、現地法人（日本・韓国・欧州・中国）、組織（事業部・チーム・課）。元データは自社システムのCSV。全員が全データを閲覧。部門長が月次定例で確認し、担当者が説明、必要に応じて上層部へ。Microsoft 365・Power BI・DOMO あり。Python 保守者あり。 |
| 仮置き | 締めは月末、到着期限は翌月第5営業日、定例は第8営業日、会計年度は4月始まり、30日で転換判定、組織は「商品×国内/海外」で課が決まる、1受注＝1商品・1課・1顧客、為替は予算レートで評価。 |
| 未確定 | 各KPIの分母と計上日、原価の種類、目標の粒度、閾値、担当者の割り当て、組織と明細の紐付け方。 |

## 1. 技術構成と理由

| 層 | 採用 | 理由 |
|---|---|---|
| 取込・集計・分析 | Python + DuckDB（SQL） + pandas | 保守者がいる。サーバー不要。KPIの計算式をSQLで書け、定義ファイルから生成できる。シナリオで自動検証できる。 |
| 出力 | CSV（UTF-8 BOM）・Parquet | Power BI・DOMO のどちらからも読める。BIを替えても集計ロジックは共通。 |
| 閲覧 | Power BI（推奨）＋確認用HTML | M365 の中で権限・共有・Teams埋め込みが完結。HTMLは画面構成の検証と、BI構築前の確認用。 |
| 人の確認 | 本番は Microsoft Lists（ダミーでは `config/review/*.csv`） | Power BI は閲覧専用のため、確認状況・担当・期限・コメントの入力先が別に必要。変更履歴が残る。 |
| 通知 | Power Automate → Teams（通知予定リスト `notifications.csv` まで実装。送信は未接続） | 充足率80%超のサプライヤ担当・上司への通知、P1 と上層部へのエスカレーション。 |

DuckDB は単一スレッドで実行しています（並列集計では浮動小数の加算順が変わり、再実行で1円未満の差が出るため）。

## 2. KPI設計

- **定義は1KPI＝1ファイル**（`config/kpis/*.yaml`）：名称、説明、種類（合計／比率）、表示、良い方向、集計元ビュー、分子・分母のSQL式、除外条件、依存する元データ、成熟期間、担当の既定値、未確定の論点、版と状態（provisional／approved）。
- **比率は分子・分母を最小粒度（月×法人×商品×課×顧客）で保持し、合計してから割る**。率の平均は取りません（`tests/test_units.py`）。
- **成熟期間**：見積→受注転換率（30日）と品質不良発生率（不良の発見遅れ30日）は、直近月が確定しません。ダッシュボードで「成熟待ち」と表示し、アラートは直近の成熟済み月（例：7月）で判定します。
- **目標**：`targets.csv`（KPI×月×内訳）。ダミーでは全社・法人・商品の単位に置いています。目標がない内訳では目標差を計算しません。
- **担当者**：`owners.csv`（KPI×法人×商品、`*` は全体）。最も具体的に一致した行を採用します。
- **データの出所**：各実行で、取込ファイルのハッシュ、実行ID、設定の版（Gitのコミット）、閾値の状態を `manifest.json` とダッシュボードのヘッダーに記録します。

仮の定義（要確認）：

| KPI | 仮の計算式 | 決めること |
|---|---|---|
| 受注金額 | 受注日が当月・取消以外の明細金額 × 予算レート | 税抜/税込、取消の計上月、換算レート |
| 受注件数 | 受注日が当月・取消以外の受注番号数 | 受注番号単位か明細単位か、複数商品の受注の有無 |
| 見積→受注転換率 | 見積日が当月の見積のうち、30日以内に受注したもの | コホート方式か簡易方式か、判定日数 |
| 粗利率 | （受注金額−原価）÷受注金額 | 見込み原価か実際原価か |
| 納期遵守率 | 回答納期が当月の明細のうち、納期内に出荷した割合（未出荷の納期超過は未達） | 回答納期か希望納期か、出荷日か着荷日か |
| 品質不良発生率 | 出荷月に帰属させた不良件数 ÷ 出荷明細数 | 出荷月帰属か発見月帰属か、社外のみか社内不適合も含むか |

## 3. データ取込

- **着地**：`landing/<batch>/<source>/<法人>/<source>_<法人>_<YYYYMM>[_接尾辞].csv` と管理ファイル（件数・金額合計）。後から届いたバッチほど新しいとみなします。
- **列対応**：`config/sources/<profile>/sources.yaml` に「元の列名 → 標準列・型・必須・許容値・最小値・参照マスタ」。
- **停止する（blocking）もの**：必須列がない（列名変更）、管理ファイルと件数・金額が合わない、為替レートがない、マスタ不備。黙って進めるとKPIが誤るためです。停止時はDQレポートだけを出力し、前回の公開結果は変えません。
- **行単位の不正は隔離**：必須欠損・形式不正（存在しない日付など）・範囲外（負の金額）・許容値外。隔離行は理由付きで `quarantine.csv` に残します。
- **形式違いの吸収**：NFKC正規化（全角数字・全角記号）、桁区切り、複数の日付形式、文字コードの自動判別（想定と違えば情報として記録）。
- **重複**：同一内容のファイル再送は読み飛ばし。同じファイル内の完全重複行は1行にまとめて件数を記録。同じキーで内容が違う行は更新日時が新しい方を採用し、同じファイル内なら要確認（P2）、別ファイル（再抽出）なら更新として情報記録。
- **未登録コード**：「未分類（UNK）」として集計し、合計は一致させたまま件数を報告。
- **更新遅延**：法人×データ×月ごとに到着を確認。期限（翌月第5営業日・仮）を過ぎた未着は P1。未着のデータを含むKPIは「未着／一部未着」と表示し、**業績アラートの判定を保留**（数字の欠けを業績悪化と誤認しない）。
- **過去データの修正**：毎回、届いたファイル全体で再集計し、前回のスナップショットと比べて修正ログを作成。「暫定値の確定」（未着だった月が届いた）と「過去値修正」（確定済みの月が変わった）を区別し、5%以上（率は1pt以上）の修正は P2 で通知。

## 4. 月次分析

- **当月値・前月差・前月比・前年同月比・3か月移動・年度累計・目標差・達成率**。率のKPIの差は pt で表示。
- **前月値がない場合**：「新規」「前月0」「データなし（未着）」を区別し、前月比は計算しません。
- **季節性を考慮した見込み値**：`直近3か月の水準 × 過去1〜2年の同月の「直前3か月→当月」の動き`。率のKPIは差で同様に計算。
  見込みとの乖離を、過去24か月の乖離のばらつき（MAD）で割った **z** で「いつもと違うか」を測ります。
  欧州の8月休暇のような毎年の落ち込みは見込みに織り込まれ、急変とは判定しません（シナリオ S5）。
- **要因の分解**（原因の断定はしない。データで言えることだけ）
  - 受注金額：件数の変化による分 ＋ 単価の変化による分
  - 率のKPI：商品構成の変化による分 ＋ 各商品の率の変化による分（合計は全体の差に一致。S4）
  - 内訳ごとの寄与：どの法人・商品・顧客が変化を生んだか
  - 大口案件：1受注が法人×商品の月額の12%以上 → 注記。翌月の減少には「反動の可能性」と注記（S6）

## 5. アラート

| 種類 | 判定（仮の閾値） | 優先度 |
|---|---|---|
| 目標未達 | 達成率 < 90%（P2）/ 80%（P1）。率は目標差 −1.5〜−3pt など KPI別 | P1/P2 |
| 急変 | 見込みからの乖離 z ≧ 3.5（P2）/ 5.0（P1）。全社の10%以上の影響は P1 | P1/P2 |
| 連続悪化 | 3か月連続で悪化し、累計の変化が平常のばらつきの2倍以上 | P3 |
| 季節要因の可能性 | 前月比は−15%以上悪化だが、過去の同月も同様に低下し、見込みの範囲内 | 情報 |
| 大口案件 | 上記の注記 | 情報 |
| データ品質 | 未着・停止事項は P1、隔離・未登録コード・同一ファイル内の矛盾は P2 など | P1〜情報 |

**誤検知を抑える仕組み**

- 母数が小さい内訳は判定しない（例：納期遵守率は納期到来明細が30未満。S8）
- 影響が小さい変化は出さない（全社値の1%未満、遅延明細5件未満など）
- 率の目標未達は、標本誤差の2倍以上の差のみ
- データ未着・成熟待ちの内訳は判定を保留
- 上位の内訳でも出ているアラートは関連付け、上位が平常なら「内訳のみ悪化」と表示（S3）
- 前月差が小さい目標未達は「今月新たに起きた変化ではない」と明示し、前月差の分解（ノイズ）を根拠にしない（S2）

閾値はすべて `status: provisional`。本番では実データ24か月で遡って「月に何件出るか」「過去の既知の問題を検知できたか」を確認して決め、承認者を記録します。
S0（通常推移）で P1・P2 がゼロになることを、誤検知の基準として検証しています。

## 6. アクション提案

- **1つの事象に1件**：同じKPIで複数の内訳にアラートが出たとき、
  - 今月の変化が特定の下位内訳に集中（寄与60%以上かつ普段の構成比の1.5倍以上）し、その内訳でもアラートが出ている → 最も具体的な内訳に置く（S3：欧州×板金溶接）
  - 変化が広く分散 → 上位（例：全社）に置き、他の内訳は「同時にアラートが出ている内訳」として併記
  - 組織・業種・規模の切り口は、同じKPIで法人・商品側にアクションがあれば併記のみ
- **構成**：事実（データで確認済みの数値）／データから言えること（分解結果）／原因の仮説（状態：未検証・データで示唆）／確認すること／想定される影響（試算と明記）／担当・確認者・期限・状態。
- **断定しない**：仮説が人の確認で「支持」になるまで、提案の動詞は「確認」にとどめます。
- **担当・期限**：担当は owners マスタから、期限は次回定例の3営業日前（仮）。データ品質の P1 は取込日から2営業日。

## 8. 運用（月次の流れ・仮）

| 時期 | 作業 | 担当 |
|---|---|---|
| 翌月1〜5営業日 | 自社システムからCSV出力 → 着地フォルダへ | 情報システム（将来は定時出力） |
| 第6営業日 | パイプライン実行。停止事項・未着があれば出力元に確認 | データ管理者 |
| 第6〜7営業日 | 担当者が自分のKPIのアラートを確認・棄却（理由必須）し、仮説とコメントを記入 | 各担当 |
| 第7営業日 | 部門長が事前確認。担当・期限を修正。上層部に上げる事項を決める | 部門長 |
| 第8営業日（定例） | 変化点の確認、アクションの割り当て | 部門長 |
| 定例後 | `--finalize` で確定版として記録 | データ管理者 |

- 確認結果は `review.csv`（本番は Lists）に、アラートID・アクションIDで紐付けて保存します。IDは「月・KPI・ルール・内訳」から決まるため、再実行しても変わりません。
- アクセス権：閲覧は全員（ヒアリングどおり）。編集は、KPI定義・閾値はリポジトリのレビューを経て、目標は経営企画、確認結果は担当者・部門長、元データの着地フォルダはデータ管理者とパイプラインのみ。
- 社内データはリポジトリに入れません（`data/` `out/` は `.gitignore`）。顧客側の担当者名・メールアドレスは取り込まない前提です。

## 9. 毎朝の更新（日別・時間別・当月の進捗）

- **取込日＝毎朝**。データは前日まで。締め月（前月）の月次分析に加え、当月途中の値を毎回計算します。
- **期間の切り替え**：全期間（月）／半年・四半期（週、月曜始まり）／1ヶ月・1週間（日、前週同曜日と比較）／1日（時間別、前週同曜日と比較）。
  時間別は受注日時を持つ受注明細ベースのKPI（受注金額・受注件数・粗利率）のみ。見積・納期・不良は日別まで。
  業種・顧客規模の絞り込みは月単位のみ（日別データは法人・商品・組織の粒度で保持）。
- **目標線**：月はそのまま、週・日は月の目標を平日数で日割り（率のKPIは月の目標）。
- **着地見込み**：当月累計 ÷ 経過平日 × 当月の平日（単純な日割り）。経過5営業日以降、見込みが目標の90%（P2）・80%（P1）未満で、
  受注件数から見たばらつきの2倍を超える不足のときだけアラート（S21）。転換率・不良率は成熟待ちのため当月途中は判定しません。
- 営業日は現状「平日」で数えています。法人ごとの休日カレンダーは実データ接続時に設定が必要です。

## 10. サプライヤの生産充足率

| 項目 | 内容 |
|---|---|
| 定義 | 充足率（件数）＝出荷日ベースの出荷明細数 ÷（日あたり供給可能件数 × 平日数）。数量も同様。高いほど逼迫、**80%以下が目標** |
| 供給能力 | サプライヤ × 材質 × サイズ × 表面処理 × 熱処理 ごとの日あたり上限（件数・数量）のマスタ |
| 出荷日 | 出荷済みは出荷日、未出荷は納期（納期を過ぎた残は取込日）に計上 |
| 観点 | 締め月／当月累計（5営業日以降）／今後5営業日の出荷予定（受注済み分。リードタイム内でほぼ出そろう範囲） |
| 判定 | 80%超＝P2、95%超＝P1、100%超＝P1（供給能力超過）。件数・数量の高い方で判定 |
| 誤検知抑制 | 月の供給能力150件未満の組み合わせは単独で判定しない（大口1件で大きくぶれるため。サプライヤ全体では判定） |
| 打ち手 | 振替（同じ法人で同じ仕様を扱い、充足率60%未満のサプライヤと余力）／拡大交渉（80%に収めるための必要能力＝出荷÷0.8−現能力）／平準化（今後の予定で逼迫）／新規開拓（振替候補なし） |
| 通知 | サプライヤ担当（宛先）と上司（CC）へ Teams。前回の状態と比べ、新規・悪化・解消のときだけ（S19 で再実行時に再通知しないことを確認） |
| 品質・納期 | 品質不良率・納期遵守率も同じ絞り込み（法人・サプライヤ・材質・サイズ・表面処理・熱処理）で表示 |

検証：S19（逼迫・振替候補あり）、S20（能力超過・振替候補なし・今後の予定も逼迫）で、充足率が生成元から独立に計算した正解値と
全536組み合わせ・18社で一致することを確認しています。

## 11. ダウンロード

- 画面の各表・グラフに「CSV」「Excel」ボタン。表示中の絞り込み・期間を反映したデータを保存します。
  Excel は外部ライブラリを使わずページ内で .xlsx を作ります。claude.ai の公開ページでは downloads 機能（保存前に確認が出る）、
  手元でHTMLを開いた場合はブラウザの通常の保存を使います。
- パイプラインは集計結果一式を `marts/kpi_report.xlsx`（シート別）でも出力します。明細は行数が多いため Power BI／CSV で扱います。
